## 2. Описание реализации

**Хранение матриц.** Матрицы A (n×m), B (m×k) и результат C (n×k) хранятся в одномерных массивах std::vector<int64_t> с индексацией i·cols + j. Элементы — случайные целые от 0 до 9 (генератор mt19937_64, seed 42); тип результата 64-битный, переполнения нет. Умножение написано вручную вложенными циклами, библиотек линейной алгебры и автоматического распараллеливания нет.

**Порядок циклов.** В основных замерах используется порядок i → t → j: внутренний цикл идёт подряд по строке B и строке C. Для сравнения реализован и «школьный» порядок i → j → t (раздел 4.3).

**Разделение работы.** Создаётся T потоков std::thread. Строки C делятся на T непрерывных блоков: каждый поток получает n / T строк, а первые n % T потоков — по одной лишней. Если T больше n, часть потоков получает 0 строк и сразу завершается. Главный поток ждёт рабочие через join().

**Итоговая матрица.** Каждый поток записывает вычисленные элементы на их места в общую матрицу C в памяти программы. Потоки пишут в непересекающиеся строки, поэтому для C блокировка не нужна: две записи в одну ячейку невозможны, а A и B только читаются.

**Счётчик прогресса.** После каждой строки поток выполняет rows_done.fetch_add(1) для общего std::atomic<long long>. Главный поток, пока рабочие считают, каждые 20 мс читает счётчик и печатает «Прогресс: N%» только при смене целого процента; в конце выводится ровно 100%. Без синхронизации операция counter++ состоит из трёх шагов (прочитать, прибавить, записать). Два потока могут прочитать одно и то же значение и оба записать value+1, тогда одно увеличение потеряется (гонка данных): прогресс отстанет и может не дойти до 100%, а по стандарту C++ это ещё и неопределённое поведение. Атомарная операция выполняется неделимо. Общей матрице C защита не нужна, потому что у неё нет ячеек, в которые пишут несколько потоков.

**Проверка корректности.** При каждом запуске контрольная сумма всех элементов C сравнивается с независимо вычисленной по формуле Σ(C) = Σₜ (сумма столбца t матрицы A) · (сумма строки t матрицы B); программа выводит «OK» или «ОШИБКА» и завершается с ненулевым кодом при несовпадении. Скрипт замеров останавливается при любой ошибке, весь прогон завершился без ошибок. Дополнительно проверены запуски matmul 5 4 6 3 (матрица выводится целиком), matmul 3 4 5 8 (потоков больше, чем строк) и matmul 1000 1000 1000 4: везде результат «OK».

Ключевые фрагменты кода (весь код — в приложении):

```cpp
static void worker(const Matrix& A, const Matrix& B, Matrix& C, int lo, int hi, bool itj) {
    for (int i = lo; i < hi; ++i) {
        if (itj) row_itj(A, B, C, i); else row_ijt(A, B, C, i);
        rows_done.fetch_add(1, std::memory_order_relaxed);   // общий счётчик прогресса
    }
}
```

```cpp
int base = n / T, rem = n % T, lo = 0;
for (int p = 0; p < T; ++p) {
    int cnt = base + (p < rem ? 1 : 0);
    threads.emplace_back(worker, std::cref(A), std::cref(B), std::ref(C), lo, lo + cnt, itj);
    lo += cnt;
}
```

## 3. Методика измерений

Замерялось только умножение. Таймер std::chrono::steady_clock запускается после генерации матриц, перед созданием потоков, и останавливается после join() всех потоков (создание потоков входит в замер). На время замеров вывод прогресса отключён, чтобы печать не влияла на результат. Размеры квадратных матриц: 500, 1500 и 2500. При размере 2500 один поток считает около 12 с; при 3000 — около 21 с (подбор размеров скриптом run_bench.py calibrate). Числа потоков: 1…16 с шагом 1, затем 32 и 64 (т. е. 4× и 8× от числа логических процессоров, равного 8). Для каждой комбинации «размер — число потоков» выполнено 5 замеров; наибольшее и наименьшее отброшены, оставшиеся три усреднены. Перед серией сделан один неучитываемый прогревочный запуск. Замеры выполнял скрипт run_bench.py, обработку — analyze.py; ускорение S(T) = t(1)/t(T), эффективность E(T) = S(T)/T. Ноутбук был подключён к сети, остальные программы закрыты.

## 5. Анализ результатов

**Оптимальное число потоков.** Минимальное время получено при T = 8 для матриц 500×500 (0,020 с, S = 3,67) и 2500×2500 (4,569 с, S = 2,67). Для 1500×1500 минимум при T = 5 (0,978 с), но при T = 8 время 1,015 с, разница около 4% и лежит в пределах разброса замеров. Поэтому оптимальным для этой машины я считаю T = 8, то есть число логических процессоров; практически почти весь выигрыш достигается уже при 4–5 потоках. Почти линейно (эффективность около 0,8 и выше) ускорение растёт только до 2–3 потоков: E(2) = 0,93 / 0,77 / 0,76 и E(3) = 0,80 / 0,80 / 0,63 для размеров 500 / 1500 / 2500. Дальше до 4 потоков (все физические ядра) рост замедляется: S(4) = 1,99 / 2,45 / 2,14, то есть вместо идеальных 4 получено 2–2,5. Для 500×500 значение при T = 4 хуже, чем при T = 3 и T = 5; вычисление длится всего около 30 мс, и такой выброс, вероятно, вызван фоновой активностью ОС или сменой частоты процессора, отдельно я это не проверял.

**Между числом физических ядер и числом логических процессоров (T = 5…8).** Здесь потоки попадают на второй логический процессор уже занятого ядра (Hyper-Threading). Два потока делят исполнительные блоки и кэши одного ядра, поэтому полноценного удвоения нет: относительно T = 4 ускорение при T = 8 выросло на 4% для 1500 и на 25% для 2500, а для 500 в 1,8 раза (но T = 4 там выброс; относительно T = 3 рост в 1,5 раза). Выигрыш небольшой, но он есть, и именно при T = 8 получены минимумы времени.

**Потоков больше, чем логических процессоров (T > 8).** Время не улучшается. Для 500×500 оно остаётся на плато 0,020–0,025 с, чаще около 0,022 с (S ≈ 3,1–3,5). Для 1500×1500 плато 1,06–1,19 с (S ≈ 2,2–2,4), то есть немного хуже, чем при T = 5–8. Для 2500×2500 при T от 10 и выше время ухудшается до 5,9–6,6 с (S ≈ 1,9–2,1), что на 30–45% хуже, чем при T = 8 (4,57 с). Новых вычислительных ресурсов нет, планировщик ОС по очереди запускает потоки на тех же 8 логических процессорах, добавляются переключения контекста, и потоки вытесняют друг у друга данные из общего L3. Само создание даже 64 потоков заметных затрат не добавило (для 500×500 время при T = 64 такое же, как при T = 16), потому что работа каждого потока много больше стоимости его создания. Нестабильность результатов 2500×2500 при T от 6 до 16 (например, 6,49 с при T = 6 и 5,31 с при T = 7) я объясняю не только планировщиком, но и тем, что замеры шли подряд и ноутбук к этому времени мог нагреться и снизить частоту; это предположение, специально я его не проверял.

**Почему ускорение меньше идеального.** Я вижу четыре причины. (1) Память. При порядке i → t → j для каждой строки результата заново проходится вся матрица B. Для 2500×2500 это 2500 × 50 МБ = 125 ГБ данных за умножение, то есть при t(1) = 12,2 с это около 10 ГБ/с с одного потока (оценка сверху: часть данных берётся из кэша). Память у меня одноканальная DDR4-2400 с теоретическим пиком 19,2 ГБ/с, значит, один-два потока уже занимают заметную долю пропускной способности, и дальше ускорение не растёт. Для 1500×1500 оценка получается такой же, около 10 ГБ/с. (2) Частота процессора. Это энергоэкономичный процессор (серия U): в простое Диспетчер задач показывал 3,8 ГГц, но при загрузке всех ядер и нагреве частота снижается, поэтому t(1) измерено на более высокой частоте, чем работают 4–8 потоков. (3) Hyper-Threading не даёт вторых полноценных ядер. (4) Для малой матрицы время вычислений порядка десятков миллисекунд, и на него заметно влияют создание потоков и шум ОС.

**Зависимость от размера матрицы.** Малая матрица масштабируется лучше: максимум S = 3,67 против 2,65 у 1500 и 2,67 у 2500. Матрица B размером 500×500 занимает 1,9 МБ и целиком помещается в общий кэш L3, поэтому потокам меньше приходится ходить в оперативную память. У матриц 1500 и 2500 B не помещается в L3 (17 и 48 МБ), и их потолок ускорения практически одинаков (около 2,6–2,7), хотя размеры отличаются в 1,7 раза.

**Во что упирается ускорение: в ядра или в память.** Ядер хватило бы на большее: потолок ускорения на 1500 и 2500 около 2,6–2,7, а не 4. Сравнение графиков для матрицы, которая почти помещается в L3 (500), и для матриц, которые не помещаются (1500, 2500), показывает, что первая масштабируется заметно лучше. Это означает, что на больших матрицах ограничение, скорее всего, в пропускной способности памяти (в сочетании со снижением частоты при нагрузке), а не в числе ядер. Прямых измерений нагрузки на память я не делал, поэтому это вывод по косвенным признакам.

**Порядок циклов.** Для одного потока на 2500×2500 порядок i → j → t занимает 72,56 с, а i → t → j — 12,32 с, то есть в 5,9 раза быстрее при том же числе арифметических операций. В школьном порядке матрица B читается по столбцу: B[t][j] и B[t+1][j] лежат в разных строках, далеко друг от друга, и почти каждое обращение — промах кэша (кэш-линия 64 байта содержит 8 чисел int64, используется одно). В порядке i → t → j данные читаются подряд, и каждая загруженная кэш-линия используется полностью.

**Что ожидалось и что получено.** Я ожидал, что ускорение будет близко к линейному до 4 потоков и затем немного вырастет до 8. Получено существенно меньше: максимум 2,7 для больших матриц и 3,7 для малой, а на больших матрицах при T > 8 ещё и ухудшение. Объяснение изложено выше (память, частота, Hyper-Threading), часть выводов — предположения, т. к. частоту и нагрузку на память во время замеров я не фиксировал.

## 6. Тесты

Контрольная сумма сравнивается с независимой формулой при каждом запуске (в том числе при всех замерах). Ручные проверки: matmul 5 4 6 3, matmul 3 4 5 8 (T больше числа строк), matmul 1000 1000 1000 4; во всех случаях «OK».

## 7. Выводы

1. Многопоточное умножение матриц реализовано на std::thread; строки делятся поровну, результат собирается в общей матрице C, прогресс считается атомарным счётчиком и доходит ровно до 100%.
2. Оптимальное число потоков на i5-8265U (4 ядра, 8 логических процессоров) — 8, то есть число логических процессоров; при T = 8 получено минимальное время для 500×500 и 2500×2500.
3. Максимальное ускорение составило 3,67 для 500×500, 2,65 для 1500×1500 и 2,67 для 2500×2500, то есть заметно меньше числа ядер (4).
4. Почти линейный рост наблюдается только до 2–3 потоков; Hyper-Threading (T = 5…8) даёт дополнительно лишь 4–25% на больших матрицах.
5. При T больше 8 время не улучшается, а для 2500×2500 ухудшается на 30–45% из-за переключений потоков и конкуренции за кэш.
6. Малая матрица, почти помещающаяся в L3, масштабируется лучше больших, что указывает на упор больших матриц в пропускную способность памяти (у ноутбука один модуль памяти).
7. Порядок циклов i → t → j быстрее школьного i → j → t в 5,9 раза на одном потоке из-за последовательного доступа к памяти.
8. Атомарный счётчик нужен, потому что в него одновременно пишут все потоки; матрице C синхронизация не нужна, так как потоки пишут в разные строки.
